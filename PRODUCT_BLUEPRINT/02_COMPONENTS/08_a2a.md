# Agent-to-Agent (A2A)

## Arquitectura

El sistema A2A permite que el agente principal delegue tareas complejas a subagentes especializados. Está inspirado en los estándares de la industria (LangChain, Microsoft Agent Framework) pero implementado desde cero, sin dependencias de frameworks.

### Componentes
- **`AgentCard`**: Define las capacidades de un subagente (`name`, `description`, `system_prompt`, `tools`, `mode`, `model`).
- **`OrchestratorTool`**: Tool `delegate_task` que el LLM principal usa para invocar el sistema A2A.
- **`A2AStrategy`**: Interfaz para las estrategias de orquestación.
- **`SupervisorStrategy`**: LLM router que decide dinámicamente qué agente usar.
- **`SequentialStrategy`**: Pipeline que ejecuta agentes en orden predefinido.
- **`ParallelStrategy`**: Fan-out que ejecuta N agentes en paralelo con `asyncio.gather`.
- **`SwarmStrategy`**: Handoff dinámico entre agentes (el agente actual decide a quién transferir el control).

### Modos de Contexto
- **`isolated`**: El subagente empieza con contexto limpio (ideal para revisores).
- **`fork`**: La estrategia copia el historial del `context` recibido (`agent_ctx.messages = context.messages.copy()`) antes de ejecutar al subagente. Matiz importante: `OrchestratorTool.run()` llama a `strategy.execute(task, context=None)` (`orchestrator.py`), así que **desde la TUI el modo `fork` no hereda la conversación del padre**: el subagente arranca con un `ContextManager` limpio y el `system_prompt` del `AgentCard`.

### Modelo por Agente
Cada `AgentCard` puede tener un modelo específico (`model`). En la TUI se toma de `A2A_ANALYST_MODEL`, `A2A_WRITER_MODEL` y `A2A_REVIEWER_MODEL` (`app/core/config.py`): **vacío significa usar el modelo por defecto del proveedor** (se pasa `None` al crear el `AgentCard`). Si hay valor, las estrategias llaman a `get_llm(settings.LLM_PROVIDER, model=agent.model)`; si no, reutilizan el LLM del padre. Esto permite tener un `analyst` con GPT-4o (análisis profundo) y un `writer` con un modelo más barato (documentación).

### Permisos
Todas las estrategias construyen el gate del subagente con `A2AStrategy._child_gate()` (`app/core/harness/a2a/base.py`), incluida `ParallelStrategy`. Ese método usa `PermissionGate.child()`: el hijo **comparte con el padre** `ask_user`, `persist_file` y el conjunto `session_allowed` por referencia, y copia las `policies`. Así, una aprobación con `a` en cualquier subagente (o en el padre) vale para todos, y los patrones persistidos en `.harness/permissions.json` se cargan al ejecutarse. El `DelegateTool` legacy (`subagents.py`) recibe el gate de la TUI y usa `child(allow=self.tools.names())` para mantener sus tools en `Decision.ALLOW` sin alterar la política global del padre.

### Visualización
El panel de debug (F1) muestra un `Tree` con el flujo de agentes en tiempo real (`start`, `end`, `handoff`). Se emite con `log_agent_flow()` en `logger.py`.
